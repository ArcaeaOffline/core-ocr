# Device Screenshot Layout Scaling

> This document is generated by Gemini 4 Neon WITHOUT careful human review.

## Baseline Scaling

`DeviceLayout.screen_rect` maps `1280 x 720` design coordinates onto a `w x h` screenshot with `f = min(w / dw, h / dh)`.

This matches the Cocos2d-x hybrid [`ResolutionPolicy`](https://docs.cocos2d-x.org/api-ref/cplusplus/V3.4/d0/d34/_c_c_g_l_view_8h.html) pattern:

- `w / h >= dw / dh`: `FIXED_HEIGHT`, giving `f = h / dh`.
- `w / h < dw / dh`: `FIXED_WIDTH`, giving `f = w / dw`.

The vertical formula `h / 2 + (y_d - dh / 2) * f` reduces to `y_d * f` when `f == h / dh`. One expression therefore covers both widescreen and narrower screenshots without branching.

## Legacy `t1` Tablet Stage

Arcaea redesigned its results screen in v5.0 ([Arcaea Wiki: Menu Backgrounds](https://arcaea.fandom.com/wiki/Menu_Backgrounds)). Both layout eras coexist in this library, and they scale differently on non-4:3 tablets:

| Layout          | Aspect Range      | Scaling Factor `f`       |
| :-------------- | :---------------- | :----------------------- |
| `t2` (v5.0+)    | All aspect ratios | `min(w / 1280, h / 720)` |
| `t1` (pre-v5.0) | `w / h >= 1.55`   | `min(w / 1280, h / 720)` |
| `t1` (pre-v5.0) | `w / h < 1.55`    | `min(w / 1280, h / 960)` |

On non-4:3 iPads, `t1` renders inside a `1280 x 960` stage under `FIXED_HEIGHT` with full-screen background fill. The `1280 x 720` results panel sits vertically centered with `120` logical pixels of margin above and below, which reduces to `f = h / 960`.

On Android v4.7.2, `t1` stays on `min(w / 1280, h / 720)` at `1.43` and `16:10` regardless of logical DPI or resolution scale. The `960`-height stage appears to be an iPad-only branch in pre-v5.0 builds, consistent with Cocos2d-x exposing [`Platform::OS_IPAD`](https://docs.cocos2d-x.org/api-ref/cplusplus/V3.5/de/d8b/group__platform.html) separately from `OS_ANDROID`. The v5.0 redesign (`t2`) may have removed this branch and uses `min(w / 1280, h / 720)` on all devices, including 11-inch iPad Pro and `16:10` tablets.

## Why `tablet_max_aspect` Is `1.55`

Do not raise `t1.json`'s `tablet_max_aspect` to `16 / 9`. Splitting at `16 / 9` creates an abrupt 25% scale drop (`720 / 960 = 0.75`) where re-encoded `16:9` phone screenshots land after integer rounding, such as `1333x750`, `1500x844`, and `2000x1126`.

- `1.55` covers 11-inch iPad Pro at `1.432`, iPad Air at `1.439`, and iPad mini 6 at `1.523`.
- `1.55` stays below `16:10` tablets at `1.60` and avoids rounded `16:9` screenshots near `1.777`.
- No lower bound is needed at `4:3`. Whenever `w / h <= 4 / 3`, `min(w / 1280, h / 960)` equals `w / 1280` and joins the baseline continuously.

## Known Limitation

A `t1` screenshot captured on Android at `4 / 3 < w / h < 1.55` uses `w / 1280` rather than `h / 960`. Image dimensions alone cannot distinguish it from an iPad screenshot.

At `1.43`, `w / 1280` and `h / 960` differ by about 7.4%. That gap is small enough for discrete label hit counts to tie, so any dual-candidate fallback could consider ranking candidates by continuous alignment score rather than label count.
